# Architecture documentation

Проект реализует серверную часть социальной сети на Django с MVT-подходом и отдельным сервисным слоем для бизнес-правил.

## Слои проекта

| Слой | Файлы | Ответственность |
| --- | --- | --- |
| Settings | `config/settings.py` | приложения, база данных, DRF, Swagger/OpenAPI |
| URLs | `config/urls.py`, `social/urls.py`, `social/api/urls.py` | маршруты HTML и REST API |
| Models | `social/models.py` | структура данных, связи, индексы, constraints |
| Services | `social/services.py` | бизнес-логика, приватность, подписки, сообщения |
| Forms | `social/forms.py` | HTML-формы демонстрационного интерфейса |
| HTML Views | `social/views.py` | страницы для демонстрации функций |
| API Views | `social/api/views.py` | DRF viewsets и API actions |
| Serializers | `social/api/serializers.py` | JSON-представления, валидация API |
| Admin | `social/admin.py` | администрирование моделей |
| Signals | `social/signals.py` | автосоздание профиля, синхронизация счетчиков |
| Tests | `social/tests/` | проверки моделей, сервисов, HTML views и API |

## Доменная модель

Основные сущности:

- `Profile` - расширение стандартного пользователя Django;
- `Follow` - подписка или заявка на подписку;
- `BlockedUser` - блокировка пользователя;
- `Post` - публикация;
- `Tag` - тег публикации;
- `PostAttachment` - вложение публикации по URL;
- `Comment` - комментарий или ответ на комментарий;
- `Reaction` - реакция пользователя на публикацию;
- `Bookmark` - закладка;
- `Conversation` - личный или групповой диалог;
- `ConversationParticipant` - участник диалога;
- `Message` - сообщение;
- `Notification` - уведомление;
- `Report` - жалоба на публикацию или комментарий.

## Ограничения целостности

На уровне базы данных используются:

- `unique_follow_pair` - один пользователь не может подписаться на другого дважды;
- `prevent_self_follow` - запрет самоподписки;
- `unique_block_pair` - одна блокировка для пары пользователей;
- `prevent_self_block` - запрет самоблокировки;
- `unique_reaction_per_post_user` - одна реакция пользователя на публикацию;
- `unique_bookmark_per_post_user` - одна закладка пользователя на публикацию;
- `unique_conversation_participant` - один участник не дублируется в диалоге;
- `report_has_target` - жалоба должна ссылаться на публикацию или комментарий.

Также добавлены индексы для ленты, сообщений, уведомлений, подписок и комментариев.

## Правила приватности

Правила доступа к публикациям находятся в `services.can_view_post` и `PostQuerySet.visible_to`.

Публикации:

- `public` видны всем, кроме заблокированных связей;
- `followers` видны автору, администраторам и активным подписчикам;
- `private` видны автору и администраторам;
- архивные публикации скрываются из обычной ленты.

Блокировки:

- блокировка удаляет подписки в обе стороны;
- пользователи в блокировке не видят публикации друг друга;
- между заблокированными пользователями запрещены личные сообщения.

Закрытые профили:

- подписка на открытый профиль сразу получает статус `active`;
- подписка на закрытый профиль получает статус `pending`;
- владелец закрытого профиля может одобрить заявку;
- данные закрытого профиля и его публикации видны владельцу, администраторам и активным подписчикам.

## Сервисный слой

Сервисный слой нужен, чтобы бизнес-логика не дублировалась в HTML views, API views и тестах.

Ключевые функции:

- `create_post` - создание публикации и тегов;
- `get_feed_for_user` - лента с учетом приватности;
- `can_view_post` - единая проверка доступа;
- `follow_user` - подписка или заявка;
- `approve_follow_request` - одобрение заявки;
- `block_user` - блокировка и удаление подписок;
- `toggle_reaction` - создание, изменение или удаление реакции;
- `add_comment` - комментарий с уведомлениями;
- `soft_delete_comment` - мягкое удаление;
- `toggle_bookmark` - закладка;
- `get_or_create_direct_conversation` - личный диалог;
- `create_group_conversation` - групповой диалог;
- `send_message_to_conversation` - сообщение и уведомления;
- `search_users`, `search_posts` - поиск.

## Signals

`social/signals.py` содержит автоматические реакции на события моделей:

- при создании пользователя создается `Profile`;
- при создании или удалении `Reaction` пересчитывается `Post.like_count`;
- при создании, удалении или soft-delete `Comment` пересчитывается `Post.comment_count`.

Это упрощает views и API: счетчики остаются консистентными независимо от входной точки.

## REST API

API построен на Django REST Framework:

- `DefaultRouter` генерирует маршруты viewsets;
- `TokenAuthentication` используется для Postman и внешнего frontend;
- `SessionAuthentication` оставлена для удобной работы через браузер;
- `BasicAuthentication` полезна для быстрой ручной проверки;
- `drf-spectacular` генерирует OpenAPI schema, Swagger UI и ReDoc.

API не повторяет бизнес-логику напрямую: viewsets вызывают функции из `social/services.py`.

HTML-шаблоны сделаны простыми намеренно. Их задача - показать, что backend работает:

- лента;
- создание публикации;
- профиль;
- подписки;
- комментарии;
- реакции;
- закладки;
- уведомления;
- личные сообщения;
- поиск.

Основная ценность проекта находится в backend, API, правилах доступа и тестах.

## Безопасность

В проекте применены базовые меры:

- CSRF включен для HTML-форм;
- API требует token для изменяющих операций;
- приватность публикаций проверяется в сервисах и queryset;
- чужие публикации нельзя редактировать и архивировать;
- комментарий может удалить автор, автор публикации или администратор;
- диалоги и сообщения доступны только участникам;
- блокировки учитываются в ленте, реакциях, комментариях и сообщениях.

Для production дополнительно нужны:

- хранение `SECRET_KEY` в переменных окружения;
- `DEBUG = False`;
- корректные `ALLOWED_HOSTS`;
- PostgreSQL вместо SQLite;
- HTTPS;
- rate limiting;
- отдельное хранение медиафайлов;
- CORS-настройки под frontend-домен.
